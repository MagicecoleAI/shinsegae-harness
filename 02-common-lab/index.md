# Claude Code 미니앱 제작 Playbook

GitBook의 업무 설명과 Starter Kit을 Claude Code가 읽을 수 있는 프로젝트 폴더로 만들고, **계획을 먼저 확인한 뒤 작은 미니앱을 생성·실행·수정·검증하는 전체 절차**입니다.

```text
폴더 준비
→ Claude가 먼저 읽기
→ 작업계획 확인·축소
→ 최소 미니앱 구현
→ 실제 실행
→ 오류·예상차이 수정
→ 다른 관점으로 검증
→ 실패·다음 작업 기록
```

{: .important }
> Claude가 “완료했습니다”라고 말한 것은 완료증거가 아닙니다. 바뀐 파일과 실제 실행화면, 원하는 결과와의 차이, 실패한 시험을 사람이 직접 확인해야 합니다.

## 이번 실습의 완료상태

- 팀 GitBook 페이지·README·CLAUDE·예시 입력·원하는 결과·시험을 Claude가 읽었다.
- 수정 전에 Claude의 계획을 팀이 읽고 삭제·수정했다.
- `index.html`, `styles.css`, `app.js` 또는 동등한 실행파일이 생겼다.
- 브라우저나 로컬 실행으로 첫 화면을 실제 확인했다.
- 팀별 작은 변경미션 한 가지를 구현했다.
- 오류·예상과 다른 결과를 한 번 이상 수정했다.
- 경험이 적은 팀원도 Prompt 작성·계획수정·결과설명 중 하나를 수행했다.
- 실제 팀 Agent에 적용할 것과 적용하지 않을 것을 기록했다.

---

## 1. 시작 전 준비

### 필요한 것

- 팀별 Claude Code Max 지정 사용자 로그인
- [Starter Kit ZIP]({{ site.baseurl }}/assets/downloads/shinsegae-harness-starter-kits.zip)
- 우리 팀 [GitBook 하네스 페이지]({{ site.baseurl }}/03-team-harnesses/)
- 인터넷 없이 사용할 공개·더미·비식별 예시자료
- 최신 브라우저

### Starter를 복사한다

다운로드한 ZIP을 풀고 우리 팀 폴더를 원본과 다른 작업폴더로 복사합니다.

```text
starter-kits/
├── team-01-forecast-pnl/
├── team-02-weekly-report/
├── team-03-infra-request-guide/
├── team-04-mark-monitor/
└── team-05-wbs-daily-report/
```

{: .warning }
> 원본 Starter 안에서 직접 작업하지 마세요. `team-01-work`, `team-02-work`처럼 복사본을 만들어 실패해도 처음부터 다시 시작할 수 있게 합니다.

### Claude Code를 연다

Mac·Linux Terminal:

```bash
cd team-01-work
claude
```

Windows PowerShell:

```powershell
cd team-01-work
claude
```

명령이 실행되지 않으면 설치를 새로 시도하며 시간을 쓰지 말고 운영진에게 `로그인·설치 Blocker`로 알립니다.

## 2. 팀원 세 명이 함께 사용하는 법

계정 비밀번호를 공유하지 않습니다. 지정 사용자가 키보드를 사용하더라도 세 명이 판단을 나눕니다.

| 역할 | 하는 일 | 남길 증거 |
|---|---|---|
| **초보 Navigator** | 첫 Prompt와 변경요구를 자기 말로 작성 | 요청문·계획에서 수정한 내용 |
| **지정 Driver** | Claude Code 입력·파일 변경·앱 실행 | 변경파일·Terminal·실행화면 |
| **Verifier·Recorder** | 원하는 결과·실패·사람 승인 확인 | 시험결과·오류·회고 |

20~30분마다 Prompt 작성자와 결과 설명자를 바꿉니다. 경험자가 모든 Prompt와 오류수정을 혼자 처리하면 팀 실습으로 인정하지 않습니다.

## 3. 80분 미니앱 실행순서

| 시간 | 단계 | 팀 행동 | 통과증거 |
|---|---|---|---|
| 0~15분 | 읽기 | GitBook·README·CLAUDE·Sample·Expected·Test를 먼저 읽힘 | Claude의 현재 구조 설명 |
| 15~25분 | 계획 | 최소앱·변경파일·완료기준·제외기능 확인 | 팀이 수정한 작업계획 |
| 25~45분 | 첫 구현 | 입력·결과·사람 확인 3영역의 미니앱 생성 | 첫 실행화면 |
| 45~65분 | 팀 변경미션 | 팀 페이지의 작은 기능 한 가지 추가 | 변경 전후 파일·화면 |
| 65~75분 | 실행·오류수정 | 실제 실행, 예상차이 전달, 수정·재실행 | 실패·수정 기록 |
| 75~80분 | 다음 작업 | 변경·시험·미완료·실제 적용을 기록 | 회고·인수정보 |

### 시간 Gate

- **15분:** Claude가 현재 폴더와 입력→결과를 설명해야 한다.
- **25분:** UI·API·기능을 줄인 계획이 잠겨야 한다.
- **45분:** 화면 또는 실행 가능한 결과파일이 하나 있어야 한다.
- **65분:** 팀별 변경미션을 시도해야 한다.
- **80분:** 성공·실패·사람이 바꾼 결정이 기록돼야 한다.

## 4. Prompt 1 — 수정하지 말고 먼저 읽기

Claude Code가 폴더를 추측하며 바로 코드를 만들지 못하게 합니다.

```text
지금은 파일을 수정하지 마세요.

아래 자료를 먼저 읽어주세요.
- 우리 팀 GitBook 샘플 설명
- README.md
- CLAUDE.md
- miniapp-mission.md
- samples/input/
- samples/expected/
- tests/eval-cases.md

다음을 설명해주세요.
1. 실제 사용자는 누구인가?
2. 어떤 업무문제를 해결하는가?
3. 입력자료와 필수항목은 무엇인가?
4. 입력이 어떤 순서로 결과가 되는가?
5. 사람이 확인·승인할 항목은 무엇인가?
6. 오류·금지상황에서 무엇을 중단해야 하는가?
7. 폴더별·파일별 역할은 무엇인가?

모르는 내용은 추측하지 말고 `확인 필요`로 표시하세요.
아직 코드를 작성하거나 파일을 변경하지 마세요.
```

### 사람이 확인할 것

- GitBook 설명과 다른 내용을 만들지 않았는가?
- 실제 시스템·API가 있다고 가정하지 않았는가?
- 예시 입력과 원하는 결과를 정확히 찾았는가?
- 사람이 해야 할 판단을 AI가 맡지 않았는가?

## 5. Prompt 2 — 미니앱 작업계획 만들기

```text
지금까지 읽은 자료를 바탕으로 HTML·CSS·JavaScript만 사용하는
교육용 미니앱 계획을 만들어주세요.

제약:
- 외부 패키지와 Build 도구를 사용하지 않습니다.
- 외부 API·로그인·자동 발송·실제 시스템 쓰기를 하지 않습니다.
- 제공된 공개·더미 Sample만 사용합니다.
- 원본 Sample을 수정하지 않습니다.
- 첫 결과는 20분 안에 확인할 수 있어야 합니다.

계획에 다음을 포함해주세요.
1. 최소 화면 1~2개
2. 입력→처리→결과→사람 확인 흐름
3. 만들거나 바꿀 파일
4. 10~20분 단위 작업
5. 작업별 완료 확인방법
6. 예상되는 오류와 Fallback
7. 이번에 만들지 않을 기능

아직 파일을 수정하지 마세요.
```

### 계획에서 삭제할 것

- 여러 페이지와 복잡한 메뉴
- 실제 SAP·JSM·메일·크롤링·업무시스템 연결
- 로그인·DB·서버·배포
- 여러 Agent 프레임워크
- Sample에 없는 계산·판단
- 80분 안에 시험할 수 없는 기능

---

## 6. Prompt 3 — 범위를 강제로 줄이기

계획이 크거나 이해하기 어려울 때 사용합니다.

```text
현재 계획이 80분 실습에 너무 큽니다.

다음 공식만 남겨 다시 줄여주세요.
`한 사용자 + 한 예시 입력 + 한 핵심처리 + 한 결과화면 + 한 사람 확인`

반드시 구현할 것 최대 3개,
시간이 남으면 할 것 최대 1개,
이번에 하지 않을 것을 구분해주세요.

첫 결과는 고정 Sample로 만들어야 하고,
파일 업로드·외부연결·복잡한 UI는 제외해주세요.
```

## 7. Prompt 4 — 첫 미니앱 구현

계획을 사람이 승인한 뒤 사용합니다.

```text
수정한 계획을 승인합니다.
지금은 첫 작동 결과만 구현해주세요.

만들 파일:
- index.html
- styles.css
- app.js

필수기능:
1. 제공된 더미 Sample의 대표 데이터를 보여준다.
2. 핵심 처리결과를 표·카드·보고서 형태로 보여준다.
3. 오류·확인 필요 항목을 구분한다.
4. 사람이 검토·승인할 위치를 표시한다.
5. 실제 자료가 아닌 교육용 Sample임을 화면에 표시한다.

하지 않을 것:
- 외부 API
- 실제 시스템 연결
- 자동 발송·등록·수정
- 로그인·DB·패키지 설치
- 원본 Sample 변경

작업이 끝나면
- 바뀐 파일
- 실행방법
- 완료 확인방법
- 아직 구현하지 않은 것
을 알려주세요.
```

### 실행방법

패키지 설치 없이 `index.html`을 직접 열거나 다음 로컬 서버를 사용합니다.

```bash
python3 -m http.server 8000
```

Windows:

```powershell
py -m http.server 8000
```

브라우저에서 `http://localhost:8000`을 엽니다.

## 8. Prompt 5 — 실행결과 확인하기

Claude의 설명이 아니라 실제 결과를 기준으로 다음 작업을 결정합니다.

```text
현재 파일과 실제 실행결과를 기준으로 확인해주세요.

1. 어떤 파일이 바뀌었는가?
2. 실행명령과 결과는 무엇인가?
3. 화면의 입력·결과·사람 확인 위치는 어디인가?
4. Sample의 원하는 결과와 무엇이 같은가?
5. 무엇이 다르거나 빠졌는가?
6. 브라우저·Terminal 오류는 무엇인가?
7. 다음 작업 전에 반드시 고칠 한 가지는 무엇인가?

실행하지 않은 기능을 완료라고 표시하지 마세요.
```

---

## 9. Prompt 6 — 오류를 작게 수정하기

오류가 나면 “고쳐줘”만 쓰지 말고 실제 상태를 제공합니다.

```text
현재 작업에서 오류가 발생했습니다.

목표:
[이번 작업의 완료기준]

사용한 입력:
[파일명·상황]

예상 결과:
[원하는 결과]

실제 결과:
[화면·파일·오류 메시지]

최근 바뀐 파일:
[파일 목록]

이미 시도한 것:
[재실행·확인 내용]

먼저 가능한 원인을 3개 이하로 분류하고,
가장 작은 수정 한 가지만 제안해주세요.
전체 구조를 다시 만들거나 새 패키지를 추가하지 마세요.
수정 후 같은 입력으로 다시 실행할 확인방법도 적어주세요.
```

### 오류정보에서 제거할 것

- 비밀번호·토큰·접근키
- 실제 고객·직원 이름
- 실제 손익·계약·운영 로그
- 공개할 수 없는 내부 경로·정책 원문

## 10. Prompt 7 — 독립 검증하기

Builder가 만든 결과를 바로 합격시키지 않습니다.

```text
지금부터 새 기능을 만들지 말고 검증자 역할만 수행하세요.

README.md, CLAUDE.md, miniapp-mission.md,
Sample Input, Expected Output, tests/eval-cases.md,
현재 앱과 결과파일을 읽으세요.

다음을 확인해주세요.
1. 대표 정상 입력에서 핵심 결과가 나오는가?
2. 누락·중복·잘못된 형식에서 멈추거나 경고하는가?
3. 결과를 원본 입력으로 추적할 수 있는가?
4. AI가 해서는 안 되는 판단을 자동 확정하지 않는가?
5. 실제 시스템 쓰기·자동발송·금지정보를 차단하는가?
6. 사람이 확인·승인할 항목이 보이는가?
7. README만 보고 다른 사람이 실행할 수 있는가?

결과를 PASS·PARTIAL·FAIL·BLOCKED로 판정하고,
실패를 숨기지 말고 가장 먼저 고칠 한 가지만 제안하세요.
```

## 11. Prompt 8 — 막혔을 때 범위축소·Fallback

```text
이 작업은 남은 시간 안에 완료하기 어렵습니다.

현재 작동하는 것:
[실제 결과]

막힌 것:
[오류·기능]

남은 시간:
[분]

다음 순서로 범위를 줄여주세요.
1. 외부연결 삭제
2. 파일 업로드를 고정 Sample로 변경
3. 여러 입력을 한 입력으로 축소
4. 여러 화면을 입력·결과·사람 확인 3영역으로 축소
5. AI 판단을 명시 규칙+사람 확인으로 변경
6. UI가 실패하면 Markdown·CSV 결과파일로 전환

줄인 뒤 반드시 남길 파일과 완료 확인방법을 적어주세요.
```

### 20분 Blocker 규칙

| 막힌 시간 | 행동 |
|---:|---|
| 0~10분 | 오류·입력·최근 변경을 확인해 한 번 재실행 |
| 10~20분 | 다른 팀원이 원하는 결과와 변경파일 확인 |
| 20분 | Mentor에게 목표·오류·시도·필요한 결정을 요청 |
| 30분 | 기능축소·고정 Sample·결과파일 Fallback 적용 |

---

## 12. Prompt 9 — 회고와 실제 프로젝트 연결

```text
오늘의 샘플 미니앱 경험을 실제 팀 프로젝트와 구분해 회고해주세요.

실제 파일·실행·오류기록을 근거로 다음 표를 작성하세요.
1. 처음 막힌 단계
2. 잘 작동한 Prompt
3. 너무 크거나 모호했던 Prompt
4. Claude의 계획에서 사람이 삭제·수정한 것
5. 설명과 실제 결과가 달랐던 것
6. 오류를 수정한 방법
7. 실제 팀 업무에도 적용할 구조
8. Sample이라 가능했지만 실제 업무에는 적용하지 않을 것
9. 실제 적용 전에 확인할 데이터·권한·사람 승인

추측한 내용은 `확인 필요`로 표시하세요.
```

## 13. Prompt 10 — 세션 종료·인수인계

```text
새 기능 개발을 중단하고 현재 상태를 인수인계 문서로 정리해주세요.

포함할 내용:
- 오늘 목표
- 완료된 기능과 실제 결과파일
- 변경된 파일과 이유
- 실행방법
```

## 14. 좋은 요청과 위험한 요청

| 위험한 요청 | 더 좋은 요청 |
|---|---|
| “이 프로젝트 앱으로 다 만들어줘.” | “지금은 읽고, 20분 첫 결과 계획과 제외기능을 제시해줘.” |
| “UI 멋지게 만들어줘.” | “고정 Sample의 입력·결과·사람 확인 3영역만 만들어줘.” |
| “오류 고쳐줘.” | 목표·예상·실제·오류·최근 변경을 제공하고 한 수정만 요청 |
| “정확도 높여줘.” | 실패 Test ID와 원하는 결과를 제공해 같은 입력으로 재시험 |
| “Agent 여러 개로 만들어줘.” | 역할을 나눠야 하는 이유와 인수조건이 있을 때만 분리 |
| “다 됐지?” | 바뀐 파일·실행결과·Expected 차이·실패를 보여달라고 요청 |
